# Stock management

Stock changes pass through the `record_stock_movement` RPC. Each movement has an actor, timestamp, quantity, and reason. Product edits use `update_product_with_stock` to save metadata and any stock adjustment in one transaction. The database records the difference as a count adjustment with reason `Ajustare manuala din editare produs`. Unchanged stock fields do not overwrite concurrent movements. Changed balances are checked against the balance loaded when editing, and conflicts abort the whole save.

Receipts and returns increase stock, while withdrawals decrease it. Count adjustments record a difference rather than a replacement balance. All quantity inputs accept positive whole amounts, with an explicit add/subtract selector for count adjustments. The ledger retains signed differences for withdrawals, adjustments, and reversals. Negative balances are rejected, and product-row locks serialize competing movements.

Reversals create a compensating movement while preserving the original, and each movement can be reversed only once. Products are archived rather than deleted. Archived products are hidden from customers and require restoration before further movements can be recorded.

The migration preserves existing balances as `opening_stock`, with reconciliation based on `stoc_actual = opening_stock + SUM(stock_movements.quantity)`. A new product starts at zero, and a positive initial quantity is recorded as a separate receipt. If that receipt fails, the product remains and the form does not create a duplicate.

History filters include product, actor, movement type, and local calendar dates, with an inclusive ending date. After a network failure, checking the history before retrying helps establish whether the movement was saved: the database may have committed even if the response was lost.

The account-security migration precedes `202609230001_stock_management.sql`. Invalid legacy balances or thresholds abort the migration instead of silently altering data, and the matching UI is released with the schema. The editable product stock field depends on `20260928071201_product_edit_stock.sql` being applied before release. Stock product selectors query `produse` directly and do not require the optional `inventory_products` view. Product loading failures are independent of movement history failures.

`20260929213650_product_numeric_limits.sql` adds table checks for nonnegative finite prices, positive pack sizes, nonnegative opening stock, and optional legacy weight/volume columns. Existing stock and critical-threshold checks remain in force. Invalid legacy values require explicit reconciliation before the migration is applied; the migration never guesses a corrected price. These checks cover both direct writes and product-edit RPCs.

Stock (`stoc_actual`) and cart quantities are measured in whole boxes. The cart is capped directly at `stoc_actual`, without dividing by `bucati_per_cutie`, while pack size is used only for total pieces and pricing. Stored excess is capped on reading and writing. Before a request PDF is prepared, products are reloaded, quantities exceeding current stock are reduced, and out-of-stock products are removed. Packaging changes update piece totals without reducing the box limit. A cart is a local request draft rather than a stock reservation or database order.

`npm test` checks stock validation, permissions, rollback, reversals, and archiving in PGlite. `npm run test:concurrency` checks lock behavior using separate connections to a disposable PostgreSQL instance.

For deployments missing the admin dashboard objects, `20260929214926_restore_admin_audit_inventory.sql` independently restores `public.audit_logs`, `public.inventory_products` (a security-invoker view), and `public.admin_inventory_stats()`, then reloads the PostgREST schema cache. It does not enable the optional MFA rollout or change Storage policies. Audit reads use the existing administrator check. A private trigger records profile role/status/access changes and deletions prospectively, without fabricating historical entries. `tests/admin-schema.test.mjs` verifies permissions, immutable audit records, inventory queries, and repeat application.
